## TShockShareBuff（Buff 全服共享）— 需求文档阶段

调研结论（基于 tr-code-1457 + TShock-pr-3301 源码）：

- 服务器能观测玩家 buff 集合：`TPlayer.buffType[44]`，由客户端 `MessageID 50 (PlayerBuffs)` 在 buff 变化时上报，TShock `GetDataHandlers.HandlePlayerBuffList` 接管写入（GetDataHandlers.cs:3877-3907），延迟约 1 帧（Main.cs:17884-17897）。
- 服务器**拿不到剩余时间**：50 包只含 type，`buffTime` 被硬编码为 60。→ 共享时长必须由配置给出。
- 下发：`NetMessage.SendData(55, -1, -1, null, targetIndex, buffId, ticks)`；客户端 case 55 仅 `number == myPlayer` 才 AddBuff(fromNetPvP:true)。等价 `TSPlayer.SetBuff(id, ticks, bypass:true)`（必须 bypass，否则 5 秒 LastThreat 节流）。
- 移除 buff 无专用包，只能发 `55 + time=1`。
- `Player.maxBuffs = 44`，槽位满时 AddBuff 挤掉最前的非 debuff。

用户确认的设计决策：
- 共享模式两种都要，配置 `mode` 切换：`trigger`（触发式，各自独立倒计时）/ `mirror`（镜像式，全服对齐并集，靠 55+time=1 撤销）。
- 减益是否共享可配 `shareDebuff`，默认 `false`（按 `Main.debuff` 排除）；另配 `blacklist` 永不过滤。

产出：需求文档写入 `README.md`（未动代码）。下一步按该 plan 实现 ShareBuff.cs + Config.cs + BuffClock.cs。

### 补充调研：剩余时间可以拿到（服务器自计时）

- 协议层确实没有时间：50 包只写 buffType 列表（NetMessage.cs:997-1010）；服务端把 buffTime 硬编码 60（GetDataHandlers.cs:3938 / TShock 版 3938）。OTAPI 未暴露 Player.AddBuff 钩子（strings 验证）。
- **但服务器侧 buffTime[] 是自留地**：原版只在 `whoAmI == Main.myPlayer` 时递减（Player.cs:9958-9960），服务端 Main.myPlayer=255 永不递减，50 包也不覆盖。→ 服务器可写入并自己递减，得到精确剩余时间。
- 接管手法：检测到玩家自发新增 buff → 补发 `55 + T` 给触发者本人（AddBuff_TryUpdatingExistingBuffTime 取 max，只延长不缩短）→ 服务器每 tick 递减 remain。
- 时长 T 来源优先级：配置表 → `Item.buffTime` 建表（遍历 ItemID.SetDefaults，取 buffType→max(buffTime)，Item.cs:279/281）→ defaultSeconds。
- 边界：`BuffID.Sets.TimeLeftDoesNotDecrease`（宠物 8 个 id，BuffID.cs:22）不递减；`AddBuffTimeAdditivelyToCap`（94 号，cap 600，BuffID.cs:34）累加非取 max。
- 配置新增 `takeOverSource`（默认 true，连触发者时长也统一到服务器值）；移除 `scanIntervalTicks`（改为每 tick 扫描，开销可忽略）。

## 编码完成（git 已初始化，2 次提交）

已实现文件：
- `ShareBuff/ShareBuff.cs` 主体：GameUpdate 每 tick 扫描 buffType diff → 广播；TickTimers 自递减；SyncMirror（0.5s 降频）对齐并集；PlayerSlot 检测喝药；命令 on/off/reload/list。
- `ShareBuff/BuffClock.cs` Item.buffTime 建表 + 时长取值优先级 + NoDecrease 判断。
- `ShareBuff/Config.cs` 配置模型。

关键实现要点（后续维护注意）：
- `TSPlayer.SendData` 是 `NetMessage.SendData(msgType, Index, -1, ...)`，**只发给该玩家自己**，所以 `player.SetBuff()` 天然是"给某玩家加 buff"，不会广播给其他人。
- 重复喝药的处理：`GetDataHandlers.PlayerSlot` 提供 Slot/Stack/Type；维护每玩家每槽位 (type, stack) 快照，`old.type>0 && old.stack - e.Stack == 1 && (e.Type==0 || e.Type==old.type)` 判定为喝药，用 `Item.buffTime` 重置该玩家计时。客户端已自行刷新，服务器**不发 55 包**，只同步自己的计时。
- TickTimers 归零时若客户端 `buffType` 仍含该 buff → 重开一轮（兜底漏检）；否则移除。
- 宠物类（TimeLeftDoesNotDecrease）在 CanShare 里直接排除，不参与共享与计时。
- 编译：`dotnet build ShareBuff/ShareBuff.csproj`（**sln 里没挂项目，直接 build sln 会空过**）。
- 常见编译坑：`BuffID`、`PlayerItemSlotID` 需要 `using Terraria.ID`；`ConnectionState` 枚举在 TShockAPI 命名空间（TSPlayer.cs:68）。
